# 跨会话记忆与指令分层（S4 设计）

> 状态：**Draft（S4.1）**。目标：让 CubusCodingAgent 做到"换一个会话仍然认识你和这个项目"，
> 并且**每一条进入模型请求的东西都能从日志重建**（宪法不变量：模型可见 ⟺ 已记录）。
>
> 相关：[context-compaction.md](context-compaction.md)（压缩解决"装不下"，本文件解决"记不住"）、
> [versioning.md](versioning.md)、[recipe-capabilities.md](recipe-capabilities.md)、
> [mcp-seam.md](mcp-seam.md)（"先给索引、按需取全文"的同一思路）。

## 1. 问题与边界

会话之间今天什么也不共享：新会话不知道这个项目的约定（构建命令、代码风格、禁区），
也不记得上一轮做过什么决定。代价是"每开一个新会话就要重新交代一遍"。

**要解决**：①项目/用户约定自动进提示词；②跨会话记住"值得长期记住的事实"；
③需要细节时能按需取回，而不是把全部记忆塞进窗口。

**不解决**（非目标，写清楚是为了不让范围膨胀）：

- **不是知识库/RAG**：没有向量库、没有 embedding、没有互联网检索。记忆是**文本文件**，检索是关键词。
- **不是"自动学会技能"**：那属于 Agent Skills（S4b），记忆只记事实与偏好。
- **不做多用户/权限**：记忆是**本机当前用户**的（`~/.cubus/memory`），没有共享与配额。
- **不做遗忘策略的自动化**：先只做"追加 + 人工可删"（文件就是唯一真相，用户能直接编辑）。

## 2. 决定 1：指令分层 —— 三层，后层覆盖前层

| 层 | 来源 | 谁负责 | 变不变 |
|---|---|---|---|
| 角色层 | 产品提示词（`CUBUS_CODING_AGENT_PROMPT`） | 产品（代码里，随 recipe 版本走） | 随产品版本 |
| 用户层 | `~/.cubus/instructions.md`（可选） | 使用者本人 | 用户随时改 |
| 项目层 | 工作区根目录 `AGENTS.md`（可选，兼容 `CLAUDE.md`） | 项目仓库 | 随仓库变 |

**顺序即优先级**：拼接顺序 = 角色 → 用户 → 项目，**冲突时后面的赢**（提示词里明确写一句
"下面的项目约定优先于上面的通用说明"）。理由：越靠近具体项目的规则越具体，具体优先。

**每层都有上限**（默认单层 8k 字符、合计 16k 字符）：超限时**截断并显式标注**
（`（AGENTS.md 超过 8000 字符，已截断）`）——宁可让模型知道"这里少了东西"，也不要静默丢失。

**注入方式**：作为 system prompt 的**片段**（`order` 决定位置：角色 0、用户 100、项目 200），
走既有的 `SystemPromptService` —— 不新增 seam、不改循环。

## 3. 决定 2：指令文本必须进日志（不是只记路径和哈希）

**问题**：`AGENTS.md` 是**可变外部输入**。只记路径 + 哈希的话，文件一改，这条会话当时
"到底给模型看了什么"就重建不出来了 —— 违反不变量。（产品提示词不一样：它在代码里，
由 recipe 版本锁定，所以记 `fragmentId` 就够。）

**决定**：装配时把三层指令的**全文**写进 `session/mount.config.instructions`：

```jsonc
"instructions": [
  { "source": "project", "path": "AGENTS.md", "chars": 4213, "sha256": "…", "truncated": false, "text": "……" }
]
```

- 放 `config` 里是**加法式**的：`config` 是"这次怎么跑的"的自由 JSON，不加事件类型、**不动格式版本**；
- 每层记 `path`/`chars`/`sha256`/`truncated`/`text` —— 审计时能一眼看出"是哪一份、有没有被截"；
- 代价：日志里多几 KB（这些文本本来每次请求都在发，不算额外开销）。

## 4. 决定 3：记忆存储 = 本机 append-only 文件，索引注入、全文按需取

**存储**（`~/.cubus/memory/memory.jsonl`，一行一条，append-only —— 与会话日志同一个套路）：

```jsonc
{ "id": "m-2026-10-13-001", "at": "2026-10-13T…", "tags": ["order", "决定"],
  "text": "order 服务默认超时定成 2500ms（比原先 5000ms 小一半）",
  "source": { "sessionId": "…", "turnId": "…" } }
```

- **id 稳定**：`m-<日期>-<序号>`，人读得懂、也能在会话里引用；
- **source 指回会话**：每条记忆都能追到"哪次会话的哪个回合说的"（可审计）；
- 用户可以直接编辑/删除这个文件 —— **文件是唯一真相**，没有隐藏数据库。

**注入的只是索引**：每次装配取**最近 N 条**（默认 12 条）渲染成一行一条
（`m-…-001 [order,决定] order 服务默认超时定成 2500ms…`）作为 system prompt 片段，
并写明"需要细节就用 `recall_memory` 工具按 id 或关键词取回全文"。

**为什么是索引**：和 MCP 的结论一致（[mcp-seam.md §4](mcp-seam.md)）——"名字便宜、正文贵"。
索引给模型**知道有什么**的能力，全文留给按需检索。

## 5. 决定 4：读取用工具，写入用"提炼回合"（都进日志）

**读**：`recall_memory` 工具（`inject: ['memoryStore']`，只读本机记忆）：

- `{ id }` → 取某条全文；
- `{ query, limit? }` → 关键词检索（按命中数与新旧排序，返回若干条全文，**有上限**）；
- 输出**永远有上限**（单次 ≤ 8k 字符，超出提示继续检索）——不让"回忆"自己撑爆窗口。

**写**：`remember_memory` 工具（模型显式记一条）+ **后台提炼**（会话结束后由一次模型调用
把"值得长期记住的事实"提炼成候选，去重后追加）。两条路径都：

1. **写进会话日志**（工具调用本身就是 `tool/call`+`tool/result` 事件；提炼那次模型调用记
   `request/header`+`assistant/message`+`usage`）——满足"模型可见 ⟺ 已记录"，也让"这条记忆
   是谁、在哪次会话写进去的"可追溯；
2. **去重**：与已有条目做规范化文本比较（去空白/大小写），重复的不再追加；
3. **失败不影响任务**：提炼失败只是没有新记忆，绝不阻断会话。

## 6. 决定 5：能力面不新增 kind

记忆需要的是"读写本机文件"，那就是既有的 `fs` 能力（和 MCP 不是第九种能力同一个理由）。
记忆插件 `inject: ['fs', 'sessionLog', 'llm', 'systemPrompt']`，**装配快照里能看到**
"这次带了几条记忆索引、指令来自哪几个文件"。

## 8. 风险与诚实边界

- **记忆会写错**：模型提炼可能记下过时或错误的事实。缓解：条目带 `at` 与 `source`（可追溯）、
  文件可手改、注入时按新旧排序（新的更靠前）。**不**做自动纠错（那是另一个课题）。
- **索引会占窗口**：N 条 × 一行。N 和单行长度都有上限，且会进装配快照（可审计）。
- **隐私**：记忆默认写在本机 `~/.cubus/memory`，不进仓库；README 的"安全模型"一节要补一句。
- **不注入全文**：所以"模型没去检索"时它就是不知道细节 —— 这是刻意的取舍（窗口换召回），
  S4.6 的评测正是要量出这个取舍的代价。

## 9. S4.2 实测（2026-10-13）

**分工**：app 读文件（用户层在工作区外，fs 能力按设计拒绝越界路径）、插件只渲染**已解析的层** ——
所以快照里的文本与模型看到的文本是同一份数据，没有"读两次"的竞态。

**行为验证**（真模型）：工作区放一份 `AGENTS.md`（"回答必须以 `[PROJ]` 开头；项目代号 CEDAR-9"），
跑一次 CLI 任务"这个项目的代号是什么？"：

```
assistant: [PROJ] CEDAR-9
```

模型同时遵守了**格式**与**事实**，说明项目层确实进了系统提示。

**日志证据**（`session/mount.config`）：

```jsonc
"instructions": [
  { "source": "project", "path": "AGENTS.md", "chars": 97, "truncated": false,
    "sha256": "60d3e4306c8f38d2…", "text": "# 这个项目的硬性约定\n\n- 回答任何问题都必须以 …" }
],
"instructionNotices": []
```

另外确认：`request/header` 里**记了每一步的 systemPrompt** —— 指令层因此有两条独立的审计路径
（装配快照里的原文 + 每步请求里的实际拼装结果）。

## 10. S4.3 实测（2026-10-13）

**分工与指令层一致**：app 造 store（它知道路径和本机 IO）、插件只渲染索引并提供 `memoryStore` 服务。

**行为验证**（真模型，工作区是**空目录**——事实只存在于记忆文件里）：

```
$ pnpm run cubus -- coding --workspace /tmp/cubus-mem-workspace \
    --task "长期记忆里，order 服务的默认超时是多少毫秒？只回答数字。" \
    --memory /tmp/cubus-mem/memory.jsonl --sessions-dir /tmp/cubus-mem-sessions
assistant: 2500
```

**日志证据**：

- 装配快照 `session/mount.config.memory` = `{ path, entries: 2, indexLimit: 12 }`（"这次带了几条"可审计）；
- `request/header.systemPrompt` 里是索引段本身：

```text
## 长期记忆（索引）

以下是跨会话记住的条目（只有索引，正文按需取回）。需要细节时用 recall_memory：
按 id 取单条，或按关键词检索。

- m-2026-10-13-002 [发布] 发布窗口固定在每周四下午，周一不发版
- m-2026-10-13-001 [order,决定] order 服务的默认超时定成 2500 毫秒（比原先的 5000 小一半）
```

- 记忆文件里**故意留了一行坏 JSON**：解析失败只被计数，并在提示里附一句"有 1 行无法解析，已跳过"——
  人可编辑的文件必须能承受写坏一行（其余条目照常可用）。

**为什么索引里给 id**：模型可以先用 `recall_memory({id})` 精确取回，不必靠关键词猜。

## 11. S4.4 实测（2026-10-13/14）

**两个工具**（都由 `withMemory` 一起扩声明 + 挂载，产品自己不用改）：

| 工具 | 作用 | 纪律 |
|---|---|---|
| `recall_memory` | 按 `id` 取一条正文，或按 `query` 关键词检索（命中数 → 新的在前） | 单次输出 ≤ 8000 字符；找不到时**告诉模型记忆里总共几条、最近有哪些 id**，而不是只说"没有" |
| `remember_memory` | 显式记下一条长期事实（去重，重复时返回原 id） | 写入本身就是一次工具调用 → **进日志**，可回放"记了什么、什么时候记的" |

**行为验证**（真模型，工作区空目录）：

记忆正文 161 字符、索引只显示前 120 字符，**编号 `ZEBRA-42` 只出现在被裁掉的那一段**。
一次任务里问两件事（取编号 + 记新事实），模型的动作全部落在日志里：

```
recall_memory   {"id":"m-2026-10-13-001"}
remember_memory {"text":"灰度开关名为 enable_new_pricing，默认关闭。","tags":["灰度","开关","配置"]}
```

- **取回成功**：模型答出 `ZEBRA-42`（它只能来自 `recall_memory` 的返回，索引里没有）；
  它还主动区分了"记忆条目的 id `m-2026-10-13-001`"与"业务编号 `ZEBRA-42`"。
- **写入成功**：记忆文件真的多了一条 `m-2026-10-14-001`（文件是唯一真相，可以直接查看/编辑）。
- 这次会话声明的工具面：`bash, edit_file, read_file, read_session_log, recall_memory, remember_memory, write_file`。

**"写入也在日志里"的含义**：`remember_memory` 的效果是"改了本机文件"，
而这次工具调用（参数 + 返回）是日志事件 —— 所以"模型能记住什么"这件事本身是可审计的。

**还没做**：自动提炼（S4.5）、跨会话召回评测（S4.6）。

## 12. S4.5 实测（2026-10-14）

**核心**（`@cubus/memory`）：`parseMemoryCandidates`（先 JSON、失败退化成"一行一条"，两种路径都过滤空条目）、
`storeCandidates`（逐条写入，去重由 store 负责，单条失败不影响其余）、`extractMemories`（自己调模型，
供离线脚本用），以及 `EXTRACT_SYSTEM_PROMPT`（明确"只记下次仍然成立的事实"）。

**触发方式（与设计的一处偏差，写清楚）**：`--extract-memory` 时，CLI 在任务结束后**再走一个正常回合**
（user 消息 = `EXTRACT_INSTRUCTION` 维护指令），然后解析那条回答并写入。

- **为什么这样做**：那次 `request/header` 与 `assistant/message` 因此天然落在会话日志里 ——
  不需要内核认识"提炼"这个概念，也不需要新事件类型或格式版本。
- **偏差**：这个回合用的是**产品提示词**（不是 `EXTRACT_SYSTEM_PROMPT`），提炼要求写在 user 消息里；
  `extractMemories()` 那条"专用模板"的路径目前只被单测覆盖，还没接进 app 流程。

**实测**（真模型，空工作区，任务里含两条约定）：

```
turn/start 次数: 2                ← 任务回合 + 提炼回合
user: 我们这个项目决定：所有时间相关的配置一律用毫秒为单位…
user: （系统维护请求，与上面的任务无关）请回顾本次会话，把值得长期记住的事实提炼成 JSON 数组…
request/header: 4 · assistant/message: 4
工具调用: remember_memory, remember_memory, bash, bash
```

提炼回合的回答（在日志里，逐字可查）：

```json
[{"text": "项目约定：所有时间相关的配置一律使用毫秒为单位，不使用秒。", "tags": ["约定","时间单位","配置"]},
 {"text": "项目约定：缓存键前缀统一使用 cart:v3:。", "tags": ["约定","缓存","键前缀"]}]
```

这两条**与模型在任务中自己用 `remember_memory` 记下的内容完全一致** → `storeCandidates` 全部判为重复，
记忆文件**没有多出条目**。也就是说：去重这条纪律在真实流程里被验证了（而不是只在单测里）。

**还没做**：跨会话召回评测（S4.6）、工作台里的"一键提炼"入口、按会话结束自动触发（目前是 CLI 显式开关）。

## 13. S4.6 实测：跨会话召回（2026-10-14）

`pnpm run eval:recall`（脚本 `packages/evals/evals/src/recall.ts`）：

1. **会话 A** 逐轮种下 6 条持久事实 + 2 条**临时状态**（正确行为是**不要**记住），结束时走提炼回合；
2. **会话 B**（全新会话、同一份记忆文件）逐条提问；
3. 判分两个数：**召回率**（事实题答对）与**克制率**（临时状态没被记住），并统计 `recall_memory` 被调用几次。

**结果（deepseek-chat，1 轮）**

| 指标 | 实测 |
|---|---|
| 召回率（新会话答出旧会话的事实） | **6/6 = 100%** |
| 克制率（临时状态没被记住） | **2/2 = 100%** |
| 记忆条目 | 6 条（每条事实一条，措辞干净） |
| `recall_memory` 调用 | **1 次**（只为那条 319 字符的错误码表） |

**过程中打出来的两条真结论**（比数字更重要）：

1. **"索引常常就够了"**：第一版工况里有一条 24 项、带规律的错误码表，提炼模型一眼看出规律、
   压成一句话塞进索引 —— 于是 6 条事实全部**不需要检索**（`recall_memory` 0 次）。
   换成 24 条**同等独特**的映射后，索引行（120 字符）必然装不下 → 检索被触发 1 次并答对。
   也就是说：**检索是兜底，不是主路径**；真正决定召回质量的是**提炼写得够不够紧凑、够不够准确**。
2. **去重只按"文本完全相同"，语义重复会漏**：有一轮里模型先用 `remember_memory` 写了
   "订单服务的默认超时时间改为 2500 毫秒。"，提炼回合又写了
   "订单服务默认超时改 2500ms 的背景：…" —— 两句话说的是同一件事，但文本不同，
   `store.append` 的规范化比较拦不住，于是**同一事实存了两份**（那次共 10 条）。
   这是已知限制；可能的后续：提炼时把"已有索引"一起给它并要求复用措辞，或给条目加一个规范化 key。

**还没测**：长文里的事实、多跳问题、相似事实互相干扰、以及"记忆写错"之后的纠错路径。
