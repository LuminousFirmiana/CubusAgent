# 上下文压缩（两层）

> 状态：Draft（2026-10-13，S3.0）。**这是唯一改会话词汇的一步**，评审通过后再写代码。
> 前置：[versioning.md](versioning.md)（事件词汇与版本规则）、[eval-suite-and-resume.md](eval-suite-and-resume.md)（恢复与结算）。
> 实现：**未实现**。本文是 S3.1–S3.4 的依据。

## 1. 问题

长会话最终会撞上两个东西：**单条工具结果太大**（读一个 2MB 文件）和**历史本身太长**（几百轮之后窗口装不下）。
两者的共同约束是我们自己的宪法：**日志是唯一事实源，任何进入模型请求的内容都必须能从日志重建**。
所以压缩**不能靠删日志**，只能改"**投影**"（从日志重建请求的那一步）。

一句话立场：**事实归事实，投影归投影**。日志永远完整；压缩只决定"这一次请求里，历史以什么形态出现"。

## 2. 决定 1：两层，分别在投影的两个位置生效

| 层 | 位置 | 手段 | 触发 |
|---|---|---|---|
| **第一层：工具结果预算** | 投影时，逐条工具结果 | 超限的结果在投影里换成**首尾预览 + 标记**（含 `tool/result` 的 id） | 单条 > 24k 字符，或一步内合计 > 96k 字符 |
| **第二层：会话压缩** | 投影时，整段历史 | 用一个**摘要**替代 `[0, keepFrom)` 的历史，`keepFrom` 之后逐字保留 | 锚点 token + 尾部估算 > 上下文窗口的 80% |

两层都是**纯函数级**的（同样的日志 → 同样的投影），因此"重建出来的请求"仍然可复现、可回放。

## 3. 决定 2：第一层为什么是"投影截断 + 读回工具"，而不是溢写文件

- **不在写入时截断**：那等于永久丢掉工具的真实输出，违反"日志是事实源"。
- **不用溢写文件**（参考实现的做法）也不坏，但要多三样东西：会话目录里的额外产物、归档白名单与哈希、以及"文件丢了怎么办"的失败语义。我们有一条更省的路：**全文本来就在日志里**。
- 因此：投影截断，并提供一个**读回工具** `read_session_log({ kind: "tool_output", id, offset?, limit? })`——它 `inject: ['sessionLog']`，只读**本会话**日志，按 `tool/result` 的 id 取回全文（支持分页）。模型看到预览里的 id 就能自己读回。
- 同理，第二层压缩掉的**原始消息**也可以用同一个工具读回（`kind: "messages"`），让"逃生通道"对称。

阈值是**投影规则常量**（导出、有单测）：`PROJECTED_TOOL_RESULT_MAX_CHARS = 24_000`、
`PROJECTED_STEP_TOOL_RESULTS_MAX_CHARS = 96_000`、预览头尾各 8_000 字符。
按 4 字符/token 估算，单条最多约 6k token、一步最多约 24k token。

**它们不是"可配项"**：投影必须只由日志决定，配置化的阈值会让同一份日志在不同机器上重建出不同请求
（回放与审计都会失真）。因此改这些常量等于改投影规则，必须与一次版本记录一起做
（见 [versioning.md](versioning.md) §2 的补充规则）。

## 4. 决定 3：第二层用**一个新事件**表达"历史已被摘要替代"

```ts
| {
    type: 'context/compacted'
    /** 摘要正文。**这是模型可见内容**：它替代了被压缩的历史，必须原样记录。 */
    summary: string
    /**
     * 投影边界：日志下标。投影时 [0, keepFrom) 被 summary 替代，[keepFrom, …] 逐字保留。
     * 记录的是**调整后**的值（见"配对安全"）。
     */
    keepFrom: number
    /** 触发原因。 */
    reason: 'threshold' | 'manual'
    /**
     * 生成摘要的输入：**日志区间 + 模板版本**。
     * 不重复存输入正文 —— 输入就是 [from, to) 这段日志，可原样重建；模板是版本化的常量。
     */
    input: { from: number; to: number; template: 'compact-v1' }
    /** 这次摘要调用的真实用量（成本可审计）。 */
    usage?: LlmUsage
    /** 压缩前后的估算 token（判断"值不值得"，也是页面上显示的数字来源）。 */
    before: number
    after: number
  }
```

**投影规则**（`deriveMessages` 的改动）：取**最后一个** `context/compacted`；
若存在，消息序列 = `[summary 作为一条 user 消息]` + 日志中 `keepFrom` 之后的所有消息事件（跳过压缩事件本身）；
若不存在，行为与今天完全一致。

**配对安全**：`keepFrom` 落在 `tool_use ↔ tool_result` 中间时向前/向后吸附到配对边界，并把**调整后的值**记进事件 ——
否则重建出的请求会被 provider 判为非法。这条要有单测（构造边界落在配对中间的日志）。

**版本**：新增事件类型 ⇒ `SESSION_FORMAT_VERSION` **3 → 4**，按 [versioning.md](versioning.md) 的五步走（加类型 → 升版 → 检查投影 → 测试 → 更新文档），
并且**旧读者读新日志会拒绝**（不静默降级）；新读者读旧日志（v3）行为与今天一致。

## 5. 决定 4：什么时候压、谁来压

**扩展点**：`LoopConfig.beforeRequest?: () => Promise<void>` —— 循环在 `step/start` 之后、写 `request/header` **之前** await 它（一次调用）。
这是本步唯一的循环改动，理由：压缩必须在"下一条请求被拼出来之前"完成，而循环是唯一知道这个时刻的人；
用**可选的、默认不存在**的钩子接入，没有压缩策略时循环行为与今天逐字一致。运行时把它接到 `ctx.get('contextCompaction')?.prepareNextRequest()`（晚绑定，插件顺序无关）。

**触发判断**：以最近一次 `assistant/message.usage.promptTokens` 为锚点，加上锚点之后新增内容的估算（4 字符/token），
超过 `contextWindow × 0.8` 就压。没有 usage 的日志（假模型/旧日志）退化为纯估算。

**摘要请求也进日志**（明确要求）：它是一次真实的模型调用，所以：
- 输入不重复存 —— `input: { from: 0, to: keepFrom, template }` 指向日志区间；
- 用量记进 `usage`；
- **投影跳过压缩事件本身**（它是"关于历史的事实"，不是历史）。

**keepFrom 怎么选**：从尾部往回走，直到保留区达到 `keepRecentTokens`（默认 8k token）或 `minKeepMessages`（默认 4 条），
且不超过 `maxKeepTokens`（默认 24k）；下限是"当前 step 的工具结果 + 至少 2 条消息"，保证压缩后请求仍然合法。

## 6. 决定 5：失败、熔断与不变量

| 情况 | 行为 |
|---|---|
| 摘要调用失败 | 重试最多 2 次（走循环已有的重试语义）；仍失败则**放弃本次压缩并继续任务**（宁可撞窗口，也不要卡死） |
| 压缩后仍超限 | 下一轮把 `keepFrom` 往前推（更激进），直到下限 |
| 连续失败 | 连续 3 次失败后停止自动压缩（熔断），只记状态；手动触发仍可用 |
| 摘要为空/模板不匹配 | 视为失败（不写事件），因为"写了个空摘要"比不压更糟 |
| 工具结果读回 | 只读本会话日志；`id` 不存在 → 报错（进 `ok:false`），提示预览里给的 id |

**不变量核查**：
1. 模型可见 ⟺ 已记录：摘要正文、压缩事件本身、读回工具的输出全在日志里 ✓；
2. 完整请求可重建：投影是纯函数（同一日志 + 同一常量 → 同一请求）✓；
3. 失败 fail-closed：压缩失败**不**放行任何东西（它只是不压），与审批/沙箱的 fail-closed 不冲突 ✓；
4. 预算与压缩互不干扰：预算是"数事件"，压缩事件不改变计数（`context/compacted` 不计步、不计工具、不计 token）。

## 7. 不做的事（明确划掉）

- **不做溢写文件**（理由见 §3）；归档布局因此不变（`ARCHIVE_FORMAT_VERSION` 不动）；
- **不做 overflow 错误分类**：LLM seam 今天只有 `retryable`，没有"上下文超限"这一类；等有真实 provider 错误要分类时再做（那时可以在失败后强制压一次并重试该 step）；
- 不做摘要质量的自动打分；不做多级递归摘要的评估（保留率评测见 §8，用它说话）；
- 不改 `request/header`/`assistant/message` 的形状（压缩事件自带 `input`/`usage`）。

### 7.1 第一层的端到端实测（2026-10-13）

造一个 88KB 的文件，让模型用 `read_file` 读全文（deepseek-chat）：

| 观察点 | 实测 |
|---|---|
| 日志里的 `tool/result`（事实） | **88,011 字符，完整保留** |
| 最后一次请求里模型看到的工具结果 | **16,156 字符**（前 8k + 后 8k + 截断标记 + 读回指引） |
| 真实 `promptTokens` | 955 → **5,089**（不做预算时这一步要背约 2.4 万 token） |
| 模型能否答题 | 能：文件最后一行的编号正好落在保留的尾部里，没有触发读回 |

这条也说明"首尾保留"的设计意图：**结尾往往是最新的事实**（日志尾部、命令输出末尾、文件结尾），
只砍尾巴会把最有用的部分先丢掉。

## 8. 验收与测量

1. **投影测试**：有压缩事件的日志，重建出的请求 = 摘要 + keepFrom 之后的原样消息；没有压缩事件时与今天逐字一致；
2. **配对安全**：边界落在 tool_use/tool_result 中间时被吸附，重建请求合法；
3. **恢复一致**：压缩过的会话 resume 后，下一条请求与压缩前同一形态；
4. **读回工具**：`tool_output` 能取回被截断的全文（分页）、`messages` 能取回被摘要替代的原始消息；
5. **长会话压测**（脚本）：构造 N 轮会话跑到底，断言"窗口不溢出 + 压缩发生次数 + 峰值 token"；
6. **信息保留评测**（对应简历第 4 条）：固定一组"前缀里的事实"问题，在压缩前后各问一次，报告**保留率**；这是那条亮点的量化口径，不许只写"不丢关键上下文"。

### 7.2 第二层的端到端实测（2026-10-13）

真模型（deepseek-chat）+ 88KB 文件 + `--context-window 4000`（故意调小以强制触发）：

```
① 压缩事件次数：1
   keepFrom=46  reason=threshold  template=compact-v1
   输入区间=[0,46)  用量={"promptTokens":2578,"completionTokens":78,"totalTokens":2656}
   估算 before=5185 → after=101
② 第 1 次请求：首条不是摘要（压缩前）
   第 2 次请求：首条**是摘要** ✓
```

摘要正文（截断）：

> 用户要求用 read_file 读取 big.txt 并回答最后一行的开头数字。已调用 read_file 读取 big.txt，
> 但工具返回内容被截断……尚未得到最后一行的开头数字。后续需要重新读取该文件末尾部分……

**三个被实测打出来的设计缺陷**（都已修）：

1. **保留预算必须由窗口推导上界**：窗口 3k 时"保留 8k token 的尾巴"是荒谬的 —— 压缩后反而更超窗。
   现在 `keepRecentTokens ≤ window × 0.5`、`maxKeepTokens ≤ window × 0.6`，并且**硬上限优先于"至少保留 N 条"的偏好**。
2. **摘要输入不能被原始工具输出淹没**：第一次实现把整段前缀（含 88k 的工具结果）喂给摘要模型，
   它最后只总结出"全是占位符"。现在工具结果在摘要输入里只留 400 字符预览（全文在日志里，可读回）。
3. **摘要模板要明确禁止工具调用标记**：真实模型会把 `<｜｜DSML｜｜ calls>` 这类模板当正文吐出来，
   那会被原样带进下一次上下文。模板里已写明 "never emit tool-call markup"。

另外输入上限的处理也从"只留结尾"改成**两头都留、省略中间** —— 开头是用户请求与目标，结尾是当前状态。
