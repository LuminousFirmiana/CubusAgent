# 跨会话记忆与指令分层（S4 设计）

> 状态：**Draft（S4.1）**。目标：让 CubusCodingAgent 做到"换一个会话仍然认识你和这个项目"，
> 并且**每一条进入模型请求的东西都能从日志重建**（宪法不变量：模型可见 ⟺ 已记录）。
>
> 相关：[context-compaction.md](context-compaction.md)（压缩解决"装不下"，本文件解决"记不住"）、
> [versioning.md](versioning.md)、[recipe-capabilities.md](recipe-capabilities.md)、
> [mcp-seam.md](mcp-seam.md)（"先给索引、按需取全文"的同一思路）。

## 1. 问题与边界

会话之间今天什么也不共享：新会话不知道这个项目的约定（构建命令、代码风格、禁区），
也不记得上一轮做过什么决定。代价是"每开一个新会话就要重新交代一遍"。

**要解决**：①项目/用户约定自动进提示词；②跨会话记住"值得长期记住的事实"；
③需要细节时能按需取回，而不是把全部记忆塞进窗口。

**不解决**（非目标，写清楚是为了不让范围膨胀）：

- **不是知识库/RAG**：没有向量库、没有 embedding、没有互联网检索。记忆是**文本文件**，检索是关键词。
- **不是"自动学会技能"**：那属于 Agent Skills（S4b），记忆只记事实与偏好。
- **不做多用户/权限**：记忆是**本机当前用户**的（`~/.cubus/memory`），没有共享与配额。
- **不做遗忘策略的自动化**：先只做"追加 + 人工可删"（文件就是唯一真相，用户能直接编辑）。

## 2. 决定 1：指令分层 —— 三层，后层覆盖前层

| 层 | 来源 | 谁负责 | 变不变 |
|---|---|---|---|
| 角色层 | 产品提示词（`CUBUS_CODING_AGENT_PROMPT`） | 产品（代码里，随 recipe 版本走） | 随产品版本 |
| 用户层 | `~/.cubus/instructions.md`（可选） | 使用者本人 | 用户随时改 |
| 项目层 | 工作区根目录 `AGENTS.md`（可选，兼容 `CLAUDE.md`） | 项目仓库 | 随仓库变 |

**顺序即优先级**：拼接顺序 = 角色 → 用户 → 项目，**冲突时后面的赢**（提示词里明确写一句
"下面的项目约定优先于上面的通用说明"）。理由：越靠近具体项目的规则越具体，具体优先。

**每层都有上限**（默认单层 8k 字符、合计 16k 字符）：超限时**截断并显式标注**
（`（AGENTS.md 超过 8000 字符，已截断）`）——宁可让模型知道"这里少了东西"，也不要静默丢失。

**注入方式**：作为 system prompt 的**片段**（`order` 决定位置：角色 0、用户 100、项目 200），
走既有的 `SystemPromptService` —— 不新增 seam、不改循环。

## 3. 决定 2：指令文本必须进日志（不是只记路径和哈希）

**问题**：`AGENTS.md` 是**可变外部输入**。只记路径 + 哈希的话，文件一改，这条会话当时
"到底给模型看了什么"就重建不出来了 —— 违反不变量。（产品提示词不一样：它在代码里，
由 recipe 版本锁定，所以记 `fragmentId` 就够。）

**决定**：装配时把三层指令的**全文**写进 `session/mount.config.instructions`：

```jsonc
"instructions": [
  { "source": "project", "path": "AGENTS.md", "chars": 4213, "sha256": "…", "truncated": false, "text": "……" }
]
```

- 放 `config` 里是**加法式**的：`config` 是"这次怎么跑的"的自由 JSON，不加事件类型、**不动格式版本**；
- 每层记 `path`/`chars`/`sha256`/`truncated`/`text` —— 审计时能一眼看出"是哪一份、有没有被截"；
- 代价：日志里多几 KB（这些文本本来每次请求都在发，不算额外开销）。

## 4. 决定 3：记忆存储 = 本机 append-only 文件，索引注入、全文按需取

**存储**（`~/.cubus/memory/memory.jsonl`，一行一条，append-only —— 与会话日志同一个套路）：

```jsonc
{ "id": "m-2026-10-13-001", "at": "2026-10-13T…", "tags": ["order", "决定"],
  "text": "order 服务默认超时定成 2500ms（比原先 5000ms 小一半）",
  "source": { "sessionId": "…", "turnId": "…" } }
```

- **id 稳定**：`m-<日期>-<序号>`，人读得懂、也能在会话里引用；
- **source 指回会话**：每条记忆都能追到"哪次会话的哪个回合说的"（可审计）；
- 用户可以直接编辑/删除这个文件 —— **文件是唯一真相**，没有隐藏数据库。

**注入的只是索引**：每次装配取**最近 N 条**（默认 12 条）渲染成一行一条
（`m-…-001 [order,决定] order 服务默认超时定成 2500ms…`）作为 system prompt 片段，
并写明"需要细节就用 `recall_memory` 工具按 id 或关键词取回全文"。

**为什么是索引**：和 MCP 的结论一致（[mcp-seam.md §4](mcp-seam.md)）——"名字便宜、正文贵"。
索引给模型**知道有什么**的能力，全文留给按需检索。

## 5. 决定 4：读取用工具，写入用"提炼回合"（都进日志）

**读**：`recall_memory` 工具（`inject: ['memoryStore']`，只读本机记忆）：

- `{ id }` → 取某条全文；
- `{ query, limit? }` → 关键词检索（按命中数与新旧排序，返回若干条全文，**有上限**）；
- 输出**永远有上限**（单次 ≤ 8k 字符，超出提示继续检索）——不让"回忆"自己撑爆窗口。

**写**：`remember_memory` 工具（模型显式记一条）+ **后台提炼**（会话结束后由一次模型调用
把"值得长期记住的事实"提炼成候选，去重后追加）。两条路径都：

1. **写进会话日志**（工具调用本身就是 `tool/call`+`tool/result` 事件；提炼那次模型调用记
   `request/header`+`assistant/message`+`usage`）——满足"模型可见 ⟺ 已记录"，也让"这条记忆
   是谁、在哪次会话写进去的"可追溯；
2. **去重**：与已有条目做规范化文本比较（去空白/大小写），重复的不再追加；
3. **失败不影响任务**：提炼失败只是没有新记忆，绝不阻断会话。

## 6. 决定 5：能力面不新增 kind

记忆需要的是"读写本机文件"，那就是既有的 `fs` 能力（和 MCP 不是第九种能力同一个理由）。
记忆插件 `inject: ['fs', 'sessionLog', 'llm', 'systemPrompt']`，**装配快照里能看到**
"这次带了几条记忆索引、指令来自哪几个文件"。

## 7. 分解（一步一锁）

| 步骤 | 内容 | 验收 |
|---|---|---|
| S4.1 | 本文件（设计 + 决定） | 你评审通过 |
| S4.2 | `@cubus/instructions`：三层加载 + 上限截断 + 进 prompt + 全文进装配快照 | **已落地**（见 §9 实测） |
| S4.3 | `@cubus/memory`：存储（append-only jsonl）+ 索引注入 | 单测：追加/读取/去重/索引上限；工作台里能看到索引片段 |
| S4.4 | `recall_memory` + `remember_memory` 工具（扩声明 + 挂载） | 单测：按 id、按关键词、输出上限、找不到的报错；真实会话里模型能自己取回 |
| S4.5 | 后台提炼（会话结束触发，去重，失败不阻断，全部进日志） | 单测：提炼解析/去重/失败路径；真实会话跑一次看条目落盘 |
| S4.6 | 测量：**跨会话召回评测**（会话 A 说事实 → 会话 B 问 → 命中率） | 真模型评测脚本 + EVALS.md 记录（简历数字来源） |

## 8. 风险与诚实边界

- **记忆会写错**：模型提炼可能记下过时或错误的事实。缓解：条目带 `at` 与 `source`（可追溯）、
  文件可手改、注入时按新旧排序（新的更靠前）。**不**做自动纠错（那是另一个课题）。
- **索引会占窗口**：N 条 × 一行。N 和单行长度都有上限，且会进装配快照（可审计）。
- **隐私**：记忆默认写在本机 `~/.cubus/memory`，不进仓库；README 的"安全模型"一节要补一句。
- **不注入全文**：所以"模型没去检索"时它就是不知道细节 —— 这是刻意的取舍（窗口换召回），
  S4.6 的评测正是要量出这个取舍的代价。

## 9. S4.2 实测（2026-10-13）

**分工**：app 读文件（用户层在工作区外，fs 能力按设计拒绝越界路径）、插件只渲染**已解析的层** ——
所以快照里的文本与模型看到的文本是同一份数据，没有"读两次"的竞态。

**行为验证**（真模型）：工作区放一份 `AGENTS.md`（"回答必须以 `[PROJ]` 开头；项目代号 CEDAR-9"），
跑一次 CLI 任务"这个项目的代号是什么？"：

```
assistant: [PROJ] CEDAR-9
```

模型同时遵守了**格式**与**事实**，说明项目层确实进了系统提示。

**日志证据**（`session/mount.config`）：

```jsonc
"instructions": [
  { "source": "project", "path": "AGENTS.md", "chars": 97, "truncated": false,
    "sha256": "60d3e4306c8f38d2…", "text": "# 这个项目的硬性约定\n\n- 回答任何问题都必须以 …" }
],
"instructionNotices": []
```

另外确认：`request/header` 里**记了每一步的 systemPrompt** —— 指令层因此有两条独立的审计路径
（装配快照里的原文 + 每步请求里的实际拼装结果）。
